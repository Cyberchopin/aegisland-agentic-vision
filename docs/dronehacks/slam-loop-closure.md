# cuVSLAM v17.0.1 的 SLAM、回环与重定位：能力、实测、和 supervisor 的交互

日期：2026-10-24。环境：开发机 RTX 4060 Ti（WSL2），**不是 Orin**。所有运行都用 `--realtime`（20 fps 节流）并记录 GPU 频率；整个过程 SM 频率中位数都在 210–330 MHz，也就是 GPU 处在降频状态。数据是 EuRoC 离线回放，PX4 只在 SITL 里跑。

## 1. v17.0.1 支持什么（以官方 API 和示例为准）

来源：
- 已安装的 wheel 自带的 pybind 文档字符串；
- 发布页的 `cuvslam-docs-17.0.1.tar.gz`（Python API 页，sha256 `1a12fbf2…`）；
- tag 下的官方示例 `examples/kitti/track_kitti_slam.py`（NVIDIA Community License，只阅读，没有复制）。

| 能力 | 是否支持 | 依据与要点 |
|---|---|---|
| SLAM 模式 | ✅ | 构造 `Tracker(rig, odom_config, slam_config)` 时传入 `SlamConfig`；`track()` 返回 `(odometry_estimate, slam_pose)` |
| 回环检测与位姿图优化 | ✅ | `get_slam_metrics()`（`lc_status`、`pgo_status`、回环 landmark 计数）；`get_loop_closure_poses()` 返回最近 10 次回环 |
| 平滑的全轨迹 | ✅（只能事后用） | `get_all_slam_poses()` 用最新的位姿图重算过去的位姿。文档原话："SLAM poses from track() method will have jumps after loop closures" |
| 保存地图 | ✅ | `save_map(folder, callback)`，格式是 LMDB（`data.mdb`）。文档警告目标文件夹会被覆盖，我们的 runner 拒绝写入已存在的目录 |
| 在已有地图里定位 | ✅ | `localize_in_map(folder, ts, guess_pose, images, LocalizationSettings, start_cb, finish_cb)`，在 guess 附近做网格搜索（水平和垂直半径、步长、角度步长） |
| 地图大小控制 | ✅ | `max_map_size`：位姿图最多保留多少个位姿，默认 300，0 表示无限；`map_cache_path` 可以写盘（LMDB） |
| 同步 / 异步 | ✅ | `sync_mode`，默认 False，即 SLAM 跑在单独的线程里 |
| 回环节流 | ✅ | `throttling_time_ms`：两次回环之间的最短间隔 |
| 平面约束 | ✅ | `planar_constraints`：强制在水平面上运动，地面机器人用，**不适合无人机** |
| 位姿图查询 | ⚠️ | `get_pose_graph()` 在我们的运行里返回 0 个节点和 0 条边，原因未查明 |
| Inertial + SLAM | ✅（实测可以跑） | API 没有写限制；MH_04 和 MH_05 的 Inertial 模式都跑通了 |

|---|---|---|
| MH_04 Inertial | 0.222 → 0.124–0.140 | 0.183 → 0.081–0.082 |

图：`slam_MH_05_difficult.png`、`slam_MH_04_difficult.png`。从图上看：
- **回环事件集中在序列末尾**，也就是飞机回到起飞区、重新看到熟悉场景的时候。
- 暗段本身几乎没有回环，SLAM **不能在暗段里实时纠错**，要等飞回见过的地方才行。
- 真正把误差拉回来的，是暗段之后、飞回起飞区时的那一批回环（MH_05 约 80 s 以后）。

**确定性：** 同步模式的两次运行逐字节一致；异步模式不一致，例如 MH_04 Stereo 一次 0.074、一次 0.110。

**代价（开发机，不是 Orin）：**
- `track()` p95 增加约 5–15 ms（同步模式的回环计算在跟踪线程里做；异步模式的 p95 也增加了，原因未查明）。
- 进程 RSS 峰值 525–551 MiB，与只跑里程计时的约 530 MiB 基本相同。
- 整卡显存读数多出约 0–150 MiB，噪声大，无法精确归因。
- 地图：MH_01 全程（182 s，49 次回环）保存后是 64 MB 的 `data.mdb`，保存用时 0.18 s。

## 3. 跨序列重定位：MH_01 建图，在 MH_05 / MH_02 里定位

- 方法：guess pose 取"已知起飞点"——用真值计算，模拟赛前熟悉场地后知道自己从哪里起飞。搜索半径 2 m，步长 0.25 m，同步模式。
- 先排除自身错误：
  1. guess 的计算在 MH_01 自身上的误差是 0.7–1.8 cm、1.1–2.4°；
  2. 用 MH_01 自己的帧去定位，2/2 成功，每次 0.35–0.45 s。
- 结果（`reloc-probe-MH_0{5,2}-in-MH_01map-*.json`）：

| 被定位的序列 | 成功率 | 成功时耗时 | 失败时耗时 | 定位结果与 guess 的差 |
|---|---|---|---|---|
| MH_02（easy，与 MH_01 同类光照） | **7/8** | 0.20–1.35 s | 26 s | 1.1–5.2 cm |
| MH_05（difficult） | **1/8** | 1.6 s | 6.5–48 s | 4.9 cm |

- 原因未查明。MH_05 探测帧的亮度并不低，只有 1 帧是 15，其余在 68–117 之间。**未验证的推测：** difficult 序列录制时场景照明或布置发生了变化。
- **失败的代价很大：** 同步模式下，一次失败的定位会**阻塞 6.5–48 s**。
- **异步模式 + 定位：2/2 次段错误（exit 139）**，结果目录标为 `*-FAILED-segfault`。这一点我们无法修复（库内部问题），只能避免使用这种组合。
- 在完整运行（`*-reloc-MH_01map-*-sync-run*`）里，起点帧定位失败后，tracker 继续在自己的新世界坐标系里工作。所以"地图坐标系误差"约 13 m，这是坐标系不同造成的，不是精度问题；按 SE(3) 对齐后，SLAM 位姿 ATE 是 0.141 m。

## 4. 回环修正和 supervisor 的冲突，以及解决办法

**观察到的规律**（MH_01、MH_04、MH_05，同步和异步都看过）：
- 所有 SLAM 与里程计之间的修正，都只出现在报告了**新回环**的那一帧（异步模式下有时晚一帧）；
- 两次回环之间，SLAM 位姿的增量和里程计完全一致；
- 单次修正最大约 0.21 m、1.1°；
- `lc_status` 会连续数百帧保持 true，不能拿它判断"这一帧有没有回环"。

**设计：锚定输出 `AnchoredSlamOutput`**（`src/aegisland/loop_closure_gate.py`，4 个单元测试）
- 发布的位姿 = 锚点 ∘ 里程计增量，因此输出天然连续。
- 只有同时满足以下三条时，锚点才更新为 SLAM 位姿，并且 **`reset_counter + 1`**：
  1. 刚报告了回环（窗口为事件之后 100 ms，用来覆盖异步模式下晚一帧的情况）；
  2. 里程计本身没有跳变（每帧 ≤ 0.25 m）；
  3. 修正在预算以内：≤ max(0.15 m, 距上次锚点路程的 5%)，并且 ≤ 0.5 m、≤ 3°。
- 预算只在 MH_04 上调整过，MH_05 作为留出集。
- 其他所有修正一律**不采纳**，并记成"外来偏移"，之后判断回环修正时先把它扣掉，防止它混进下一次合法回环。这个"泄漏"问题是在 SITL 里发现的，加了专门的回归测试。
- 离线检查：16 次 SLAM 运行（MH_04、MH_05，两种模式，同步和异步）中，137 次回环修正**全部被接受，零误拒**。

**为什么用 `reset_counter`：** PX4 EKF2 的 `ev_pos_control.cpp` 在 `reset_counter` 变化时，把位置直接重置到 EV（昨天在 SIH 里已经验证）；PX4 的控制器也会根据 `xy_reset_counter` 处理设定点。这比让滤波器去和一次跳变"打架"干净。

**SITL 验证**（HIL：MH_05 Stereo 的 SLAM 运行，加上 EuRoC 真实 IMU，送入 PX4 v1.17.0 EKF2；结果 `demo-loop-closure-gate-20261024-192807`；误差用注入之前的前 38 s 做对齐）：

| 桥接方式 | EKF2 RMS | 最大 | 说明 |
|---|---|---|---|
| 只发里程计 | 0.197 | 0.393 | 基线 |
| 直接发 SLAM 位姿（会跳） | 0.144 | 0.414 | 跳变全部被 EKF2 吸收，**没有一次拒收** |
| **门控后发 SLAM**（`reset_counter`） | **0.136** | **0.324** | 5 次回环被接受，EKF2 干净地重置 |
| 门控 + 注入 0.3 m 无回环跳变 | **0.136** | 0.325 | 跳变被拒绝，对结果**零影响** |
| 门控 + 注入 1 m 假回环 | **0.136** | 0.324 | 被判超预算并拒绝，**零影响** |
| 直接发 SLAM + 注入 0.3 m 跳变 | 0.278 | 0.573 | **EKF2 照单全收**：0.3 m 在 EV 噪声门限之内 |

**这次验证过程中我自己的错误（如实记录）：**
1. 第一版门控有"泄漏"：被拒绝的偏移在下一次合法回环时被一起接受了（注入跳变的那次运行 RMS 0.185）。
2. 第一版修复过于严格：一次真实的连续回环被判超预算，之后被永久拒绝，导致 RMS 0.157。
3. 第一版对比图对整段轨迹做对齐，把故障造成的偏移摊薄了。

三个版本都保留着，并标记为 SUPERSEDED。

**还没解决：**
- 一个恰好落在回环之后 100 ms 窗口内、而且在预算以内的故障跳变，会被当成合法修正；
- 被接受的回环帧，在 supervisor v3 眼里是 `relocalized`，会被判 degraded，于是这一帧被降权（这个行为是否合适待讨论）；
- 全部基于 EuRoC 的回环量级，换场地需要重新确认预算。

## 5. 结论：比赛里要不要开回环

**建议：开 SLAM，但只用同步模式和门控输出，不在比赛中做跨地图重定位。**

1. **开 SLAM（同步模式）加门控：**
   - 收益：实时 ATE 下降 13–34%，飞回见过的区域时能把暗段后的误差拉回来。
   - 代价：`track()` p95 增加约 5–15 ms（开发机），内存基本不变；结果可复现。
   - 前提：飞行路线会回到起飞区或其他见过的区域，否则回环不会触发。
2. **不用异步模式做定位：** 两次运行两次段错误。异步模式的普通跟踪可以运行，但结果不可复现。
3. **不依赖跨地图重定位：**
   - 在光照变化的场景下成功率很低：MH_05 只有 1/8，MH_02 是 7/8；
   - 失败时同步阻塞可达 48 s，对飞行不可接受；
   - 如果一定要用，只能在**起飞前、静止时**尝试一次，设超时，失败就从零开始建图。
4. **Orin 上的代价：** 以上所有耗时都来自开发机 GPU（而且是降频状态）。Orin 上同步回环可能带来更大的 p95 尖峰，**必须在 Orin 上实测**（见 Orin 清单第 5 节）。

## 退回纯里程计的开关（2026-10-24 决定）

`GateConfig(pose_source="odometry")` 会让门控只发里程计、不动 `reset_counter`，等同于关掉 SLAM 输出。默认值是 `"gated_slam"`。比赛中启用同步 SLAM 的前提是 Orin 上实测延迟可接受，这一点尚未验证。
